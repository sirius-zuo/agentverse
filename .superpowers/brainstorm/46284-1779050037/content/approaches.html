Three approaches for Aether's orchestration model

All three honour the decisions made — SpawnPolicy, FailurePolicy, registry-backed graph, A+C memory. The difference is how the runtime executes.

A

Dataflow / DAG-first (recommended)

The user declares a workflow as a named DAG of AgentNodes. Aether's runtime does a topological sort, executes independent branches in parallel, and routes messages along edges. Routing nodes (conditional branching) are first-class — they inspect the incoming result and pick which outgoing edge fires.

Workflow::builder()
  .node("intake", intake_node)
  .node("researcher", researcher_node)
  .node("writer", writer_node)
  .edge("intake", "researcher")
  .edge("researcher", "writer")
  .build()?

Pros

  • Maps directly to all 4 topologies
  • Explicit, inspectable, serializable to JSON/YAML
  • Parallel branches automatic from DAG structure
  • Phase 2: distribute nodes across cluster trivially

Cons

  • Dynamic emergent topologies harder to express
B

Actor model

Each agent is wrapped in an Actor with a Tokio channel mailbox. Actors send messages to each other by name — the registry resolves names to mailboxes. Topology emerges at runtime from who sends to whom. Aether's supervisor manages actor lifecycle (spawn, restart).

// inside an agent's handler:
ctx.send("writer", result).await?;

Pros

  • Very dynamic — topology not fixed upfront
  • Natural for supervisor/worker patterns

Cons

  • Topology implicit — hard to inspect or visualize
  • Agents need to know each other's names (coupling)
  • Cycles and deadlocks easier to create accidentally
C

Event-driven / pub-sub

Aether has a central event bus. Agents subscribe to event types ("task.research") and publish results as new events ("task.write"). Topology is defined by subscriptions — no explicit edges.

researcher.subscribes_to("task.research")
researcher.publishes("task.write")
writer.subscribes_to("task.write")

Pros

  • Extremely loosely coupled
  • Easy to add new agents without changing existing ones

Cons

  • Workflow hard to trace end-to-end
  • Supervision and failure handling complex
  • Overkill for Phase 1 scope

Why A: The DAG approach subsumes all four topologies — a pipeline is a linear DAG, supervisor/worker is a star DAG, a router is a conditional node, arbitrary graph is just a DAG. It's explicit (inspectable, serializable), and aligns naturally with the registry-backed naming model. The actor model is powerful but trades explicitness for dynamism — a tradeoff that hurts more than it helps at Phase 1 scope.
