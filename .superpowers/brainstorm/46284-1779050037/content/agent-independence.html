Agent independence — what does it mean in Aether?

With Transport trait (B), each agent is already isolated by interface. Here's what independence means across four dimensions — pick the model that fits your intent.

Dimension 1 · Lifecycle
A

Long-running instances

Agents are created once and registered with Aether. They handle many requests over their lifetime, accumulating memory across calls. Aether holds Arc<dyn AetherAgent> references.

B

Spawned per-request

Aether holds a factory/builder. Each incoming task gets a fresh agent instance — isolated memory, no cross-request bleed. Good for stateless specialist agents.

Dimension 2 · Memory
A

Each agent owns its memory

Agents never share a memory store. Inter-agent communication is explicit message passing only — no shared state, no side channels. Clean boundary.

B

Shared / injected memory

Aether can inject a shared memory backend (e.g., a shared long-term store) that multiple agents read/write. Useful for a supervisor reading a worker's output history.

Dimension 3 · Failure isolation
A

Failure propagates to orchestrator

An agent error returns Err(…) up to Aether. The orchestrator decides: retry, reroute, or fail the workflow. Simple — no magic recovery.

B

Supervisor auto-restarts agents

Aether's supervisor detects agent failure and restarts the agent before retrying the task. Agents are treated as disposable. Closer to an Erlang/Akka model.

Dimension 4 · Identity & discovery
A

Named agents in a registry

Every agent has a name and a declared capability set. Aether routes by name or capability. Agents can be looked up, listed, replaced by name.

B

Typed roles in a workflow

Agents are defined by their position in the graph — no global registry. Identity is structural (node in a DAG), not nominal.

These are independent choices — mix and match. Click your preferred option per dimension.
