Dimension 1 — Lifecycle as a Spawn Policy

Rather than picking one model, Aether can treat lifecycle as a per-node configuration. Each agent node in the topology declares how it is instantiated and managed.

SpawnPolicy — three modes under one abstraction
// How Aether manages a given agent node
enum SpawnPolicy {
  Singleton,                         // one long-running instance
  Pool { size: usize },               // N long-running instances, load-balanced
  PerRequest,                         // fresh instance per task, dropped after
}

Singleton

One instance, always alive. All requests serialize through it.

Good for: Supervisors, coordinators, agents that accumulate conversational state across many calls.
Risk: Bottleneck under load (one at a time).

Pool { size }

N identical long-running instances behind a round-robin or least-busy load balancer.

Good for: High-throughput stateful agents (e.g., a Researcher agent handling 10 parallel queries). Phase 1 in-process; Phase 2 distributes across nodes.
Phase 2 hook: Pool members can be on different machines — same abstraction.

PerRequest

A factory creates a fresh agent per task. Instance is dropped when the task resolves.

Good for: Stateless specialists — formatters, translators, validators. Zero cross-task memory bleed by design.
Risk: Initialization cost per call (model client setup, prompt loading).
How Aether sees a workflow node
// Every node in the topology = agent factory + policy + transport
struct AgentNode {
  name: String,
  capabilities: Vec<String>,
  factory: Arc<dyn AgentFactory>,   // builds AgentVerse agents
  policy: SpawnPolicy,
  transport: Arc<dyn Transport>,    // LocalTransport in Phase 1
}

Clustering note: In Phase 1, Pool members are Tokio tasks in the same process. In Phase 2, the pool abstraction stays identical — each member just lives on a different node, and the transport swaps from channels to gRPC. No orchestration logic changes.
