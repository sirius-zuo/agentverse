Dimension 3 — Failure isolation

When an agent fails, what does Aether do?

A

Failure propagates — orchestrator decides

An agent error surfaces as Err(AgentError) to the Aether orchestrator. The orchestrator's workflow definition decides: retry the same agent, reroute to a fallback agent, or fail the whole task. No automatic recovery — behaviour is explicit and deterministic.

Pros

  • Simple — no hidden state machines
  • Workflow author controls recovery logic
  • Easy to test and reason about

Cons

  • No automatic recovery without explicit retry config
B

Supervisor auto-restarts agents (Erlang model)

Aether's supervisor detects agent failure and restarts the agent (using its AgentFactory) before retrying. The workflow layer never sees the failure. Agents are treated as disposable — "let it crash" philosophy.

Pros

  • Self-healing at runtime
  • Good for long-running Singleton agents

Cons

  • Hides failures — harder to debug
  • Restart loop risk if root cause is logic, not transient
  • More complex to implement correctly
C

Configurable per node

Each AgentNode declares a FailurePolicy: how many times to retry, whether to restart the instance, and what fallback agent (if any) to route to. The orchestrator executes the policy; the workflow author configures it.

FailurePolicy { retries: 2, restart_on_failure: true, fallback: Some("backup-agent") }

Pros

  • Best of both — explicit and configurable
  • Fits naturally onto AgentNode (already has SpawnPolicy)

Cons

  • Slightly more upfront design surface

My recommendation: C. The FailurePolicy sits on AgentNode alongside SpawnPolicy — they're two facets of the same node config. You get auto-restart for long-running Singletons and simple propagation for PerRequest specialists, all in one model.
